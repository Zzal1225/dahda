# dahda 기획서

2026-11-03 · 박찬령 (원본: Claude Doc https://claude.ai/artifact/GHmu643VLN6GWsjSBXRj2Y)

## 서비스 소개

dahda(닿다)는 마트·소상공인이 손님에게 문자를 보내고, 보낸 문자가 **닿았는지**까지 확인하는 B2B 문자 발송 관리자 콘솔입니다. 본사가 여러 지점을 한 계정 아래에 두고, 지점은 자기 주소록으로 문자를 보내며, 발송 결과는 업체 웹훅으로 돌아와 화면에 실시간으로 반영됩니다. 이름은 "문자는 보낸 순간이 아니라 도착이 확인된 순간에 끝난다"는 설계 원칙에서 왔습니다.

**문제 정의 (실무 경험에서)**

- 실무에서 다룬 문자 발송 서비스는 지점마다 아이디가 따로였습니다(같은 브랜드의 서면점·해운대점이 각각 다른 계정). 본사가 전체 발송을 한눈에 보거나, 수신거부를 지점끼리 공유할 구조가 없었습니다.
- 발송 결과는 "접수"와 "도착"이 다른데, 화면은 접수만 보여 주고 실패는 나중에 따로 찾아봐야 했습니다.
- 광고 문자 규칙((광고) 표기, 수신거부 안내, 야간 전송 제한)은 사람이 기억해서 지켜야 했습니다.

**포트폴리오로 증명할 것 (nanaki와 겹치지 않는 축)**

1. 외부 API 3종을 실패·지연·중복까지 고려해 연동: 문자 발송 API, 발송 결과 웹훅, 충전금 결제(토스페이먼츠 테스트 모드)
2. B2B 화면 역량: 10만 행 표 가상화, URL과 동기화된 필터, 엑셀 대량 업로드, 검증 규칙이 많은 폼, 역할별 권한
3. 비동기 상태 설계: 큐·재시도·멱등성·상태 전이 규칙을 DB와 화면 양쪽에서 일관되게
4. 실무 도메인 지식을 설계로 옮기기: 광고 문자 규칙을 코드로 검증, 발송 업체를 바꿔 끼울 수 있는 어댑터 구조

진행 방식: 기획 확정 → 디자인 2\~3일 → step1\~5 개발(가짜 발송기로 시작, step4에서 실제 업체 연결, 전체 약 5주 목표). 입사 지원과 병행하므로 범위가 넘치면 2차 기능부터 뺍니다. 전 회사의 화면·코드·문구는 쓰지 않고 도메인 지식만 가져옵니다.

## 사용자와 역할

조직은 **본사 → 지점** 2단계입니다(예: dahda마트 본사 → 성수점·망원점·합정점). 단일 매장만 두면 권한이 "내 것/남의 것"뿐이라 B2B다운 데이터 범위 분리를 보여 줄 수 없습니다. 역할은 본사와 지점 둘뿐입니다. 지점마다 문자 담당자가 한 명이라 지점 안에서 지점장·직원을 나누지 않습니다(실무에서도 지점 하나가 계정 하나였음). 지점 계정은 한 지점에만 속하고, 본사 계정은 지점 소속이 없습니다.

| 기능 | 본사 | 지점 |
| --- | --- | --- |
| 지점·구성원 관리 | 전체 | 자기 지점 정보 조회 |
| 충전금 결제·거래 내역 | 본사 계정 결제·조회, 전 지점 계정 조회 | 자기 지점 계정 결제·조회 |
| 주소록 (지점별 소유) | 전 지점 조회, 엑셀 내보내기 | 자기 지점 등록·업로드·수정·삭제 |
| 수신거부 목록 (본사 공통) | 조회·등록·해제 | 조회·등록 |
| 문자 작성·발송 | 본사 계정으로 발송 | 자기 지점 (광고는 본사 승인 후 발송) |
| 광고 문자 승인·반려 | 전 지점 | — |
| 발송 내역·결과 | 전 지점 + 통계 | 자기 지점 |
| 실패 건 재발송 | 가능 | 자기 지점만 |

권한은 화면(메뉴·버튼 숨김)과 서버(Supabase RLS) 양쪽에서 막습니다. 화면 쪽은 편의, 서버 쪽이 진짜 경계입니다.

**승인 흐름**: 광고 문자만 지점 작성 → 본사 승인 → 발송. 일반(정보성) 문자는 승인 없이 바로 보냅니다. 잘못 보낸 문자는 되돌릴 수 없으므로, 비용과 민원이 큰 광고만 본사가 한 번 더 보도록 합니다(브랜드 문구·광고 규칙 통제). 본사가 직접 쓴 광고는 승인 단계를 건너뜁니다.

**충전금**: 잔액은 지점마다 따로 둡니다(본사도 자기 발송용 계정 하나). 충전은 계정 주인만 합니다(지점은 자기 계정, 본사는 본사 계정). 본사는 전 지점 잔액을 한 화면에서 조회만 합니다.

**체험 계정**: 로그인 없이 "체험하기" → 샘플 본사(지점 3개, 주소록·발송 내역 포함)에 익명 로그인. 화면 상단의 **역할 전환 버튼**으로 본사·지점을 바꿔 가며 같은 화면이 어떻게 달라지는지 볼 수 있습니다. 체험 계정은 가짜 발송기로 고정되고 실제 문자는 나가지 않습니다.

## 기능 범위

1차 출시가 포트폴리오 기준입니다. 매주 말 배포된 상태를 유지하고, 아직 없는 기능은 화면에서 숨깁니다("준비 중" 버튼 없음).

| 단계 | 기능 |
| --- | --- |
| 1차 (step1\~5) | 체험하기(역할 전환) + 이메일 로그인 · 지점·구성원 관리 · 주소록(엑셀 업로드·그룹·수신거부) · 문자 작성(바이트 계산·SMS/LMS 자동 전환·미리보기·광고 규칙 검증·즉시/예약) · 승인함 · 발송 큐(가짜 발송기 + 실제 업체 1개, 재시도) · 결과 웹훅 → 진행률 실시간 반영 · 발송 내역(10만 행 가상화·URL 필터·실패 건 재발송) · 충전금(토스 테스트 결제·잔액·거래 내역) · 첫 화면(오늘 발송 건수·성공률·잔액) · CI/CD · RLS 테스트 |
| 2차 | 이미지 문자(MMS) · 이름 치환 변수 · 템플릿 저장 · 구성원 초대 메일·비밀번호 재설정 · 지점별 사용 한도 · 통계 차트 · 작업 기록(누가 언제 무엇을) · 080 수신거부 실제 연동 |

범위에서 뺀 것: 카카오 알림톡(사업자 채널 필요), 모바일 전체 대응(승인함만), 다국어, 자체 회원가입 흐름(본사가 구성원을 만듦), 오프라인·PWA, 다크 모드(nanaki에서 이미 구현), 지점 안의 직원 계정 분리(지점당 담당자 1명이라 지점 = 계정 1개), 솔루션 제공사 운영자 화면(이 기획의 "본사"는 고객사 본사. 운영자 역할은 2차에서 RLS 범위 확장으로 추가 가능).

**1차 완료 조건**

- 체험하기 → 엑셀 업로드 → 광고 문자 작성 → 본사 승인 → 발송 → 결과 반영이 배포 주소에서 동작(E2E 1개로 보증)
- 내 번호로 실제 문자 1건이 업체를 거쳐 도착하고, 웹훅 결과가 화면에 보임
- 토스 테스트 결제 → 잔액 증가 → 발송 차감 → 실패분 환불이 거래 내역으로 남음
- 다른 지점 데이터가 안 보이는 것을 RLS 통합 테스트로 확인
- 측정 수치 5개가 `docs/performance.md`에 전/후로 기록됨, CI 초록, PC 화면 캡처

## 화면 구성

PC(1280px 이상) 우선입니다. 왼쪽 사이드바 + 오른쪽 본문, 상단에 현재 지점·잔액·역할 전환(체험 계정만)이 있습니다. 태블릿(768\~1279px)은 접힌 사이드바로 같은 화면을 보여 주고, 모바일(768px 미만)은 **승인함만** 대응합니다(본사 담당자가 이동 중 승인). 다른 화면을 모바일로 열면 "PC에서 열어 주세요" 안내를 보여 줍니다. nanaki에서 모바일 반응형을 이미 보여 줬고, 관리자 콘솔은 실제로 PC에서 씁니다.

## 데이터 모델

발송 건 1개가 수신자 N개의 메시지 행으로 나뉩니다. **10만 행 표가 바로 이 메시지 테이블**이고, 웹훅은 메시지 행 하나씩의 상태를 바꿉니다. 돈은 잔액 숫자를 직접 고치지 않고 거래 기록의 합계로 계산합니다.

| 영역 | 테이블 | 핵심 열 |
| --- | --- | --- |
| 조직 | `organizations` 본사 | 이름, 생성일 |
|  | `branches` 지점 | 본사 id, 이름 |
|  | `sender_numbers` 발신번호 | 본사 id, 지점 id(null = 본사), 번호, 이름, 대표 여부 |
|  | `members` 구성원 | auth 사용자 id, 본사 id, 지점 id(본사 계정은 null), 역할 `hq / branch`. 역할과 지점 id는 CHECK 제약으로 함께 맞춤 |
| 주소록 | `contacts` 연락처 | 지점 id, 전화번호(정규화된 숫자만), 이름, 메모 |
|  | `contact_groups`, `contact_group_members` | 지점별 그룹 |
|  | `opt_outs` 수신거부 | 본사 id, 전화번호, 사유, 등록 경로 |
| 발송 | `campaigns` 발송 건 | 지점 id(null = 본사 발송), 작성자, 본문, 종류 `sms / lms`, 광고 여부, 예약 시각, 상태, 반려 사유, 수신자 수, 예상 금액, 재발송 원본 id |
|  | `messages` 수신자별 메시지 | 발송 건 id, 전화번호, 상태, 업체 메시지 id, 우리 쪽 멱등 키, 실패 코드, 시도 횟수, 다음 시도 시각, 접수·확정 시각 |
|  | `webhook_events` 수신 로그 | 업체, 원문, 서명 검증 결과, 처리 결과 (중복·역순 디버깅용) |
| 돈 | `payments` 결제 | 본사 id, 지점 id(null = 본사 계정), 토스 주문번호·결제 키, 금액, 상태 `ready / done / canceled / failed` |
|  | `ledger_entries` 거래 기록 | 본사 id, 지점 id(잔액 계정. null = 본사 계정), 종류 `charge / reserve / release / refund`, 금액(+/-), 연결 id(결제 또는 발송 건), 멱등 키 |

```ts
// 발송 건과 메시지의 상태. 화살표 방향으로만 바뀐다 (역행 금지)
type CampaignStatus =
  | 'draft'            // 작성 중
  | 'pending_approval' // 광고 문자, 본사 승인 대기
  | 'rejected'         // 반려 (사유 보관)
  | 'scheduled'        // 승인됨 또는 일반 문자, 보낼 시각 대기
  | 'sending'          // 큐에서 처리 중
  | 'completed'        // 모든 메시지가 최종 상태
  | 'canceled';        // 보내기 전 취소

type MessageStatus =
  | 'queued'    // 큐 대기
  | 'sent'      // 업체에 접수됨 (providerMessageId 있음)
  | 'delivered' // 웹훅으로 도착 확인
  | 'failed';   // 영구 실패 또는 재시도 소진 (failCode 있음)
```

**상태 전이 규칙**

- `delivered`와 `failed`는 최종 상태. 최종 상태인 행에 웹훅이 다시 와도 무시하고 `webhook_events`에만 남깁니다(중복·역순 안전).
- `queued → sent`는 큐 워커만, `sent → delivered / failed`는 웹훅만 바꿉니다. 같은 행을 두 주체가 동시에 바꾸지 않도록 역할을 나눕니다.
- 발송 건의 `completed`는 메시지 집계로 결정합니다(최종 상태 수 = 수신자 수).
- 실패 건 재발송은 원본 행을 되돌리지 않고 새 발송 건을 만들어 `retry_of_campaign_id`로 잇습니다. 원본의 결과와 집계는 그대로 남습니다.

**충전금 규칙**

- 잔액은 계정(지점·본사)마다 `ledger_entries` 합계. `charge`(+결제 금액), `reserve`(−예상 금액, 발송 접수 때), `release`(+실패분, 완료 때), `refund`(+취소 때).
- 접수 때 잔액이 예상 금액보다 적으면 접수를 거부합니다. 잔액 검사와 `reserve` 기록은 한 트랜잭션(Postgres 함수)에서 처리해 동시에 두 번 보내도 잔액이 음수가 되지 않습니다.
- 모든 거래 기록에 멱등 키가 있어 같은 결제·같은 발송 건으로 두 번 기록되지 않습니다.

**권한(RLS)**: 모든 테이블은 `members`의 본사 id·지점 id·역할로 행 단위 접근을 제한합니다. 본사는 자기 본사 전체, 지점은 자기 지점만. `opt_outs`는 본사 단위로 읽기 허용. `webhook_events`와 `ledger_entries` 쓰기는 서버(서비스 역할)만.

## 외부 API 연동

세 API 모두 브라우저가 직접 부르지 않고 서버(Next.js Route Handler, Supabase Edge Function)를 거칩니다. 비밀 키는 서버 환경 변수에만 둡니다. 업체별 세부 조건(무료 포인트, 발신번호 등록, 초당 전송 제한, 웹훅 서명 방식)은 바뀌는 정보라 구현 시작 전에 공식 문서에서 확인하고 출처를 `docs/decisions/`에 남깁니다.

```
[문자 작성·승인] → [DB 큐 messages (queued)] → [워커 pg_cron→Edge Function] → [발송 어댑터 send(batch)·멱등 키]
                                                                                        ↓ 접수 → sent
[화면 Supabase Realtime] ← [상태 전이: 최종 상태 확정] ← [웹훅 Route Handler: 서명 검증·원문 저장] ← [문자 업체 솔라피/가짜 발송기] (결과 콜백)
```

윗줄이 접수 경로, 아랫줄이 결과 경로입니다. 같은 메시지 행을 윗줄은 queued → sent로, 아랫줄은 sent → delivered / failed로만 바꿉니다.

**1. 문자 발송: 어댑터 구조**

- 공통 인터페이스 `SmsProvider { send(batch): Promise<SendResult[]>; parseWebhook(req): WebhookEvent[]; verifySignature(req): boolean }` 하나를 두고, 솔라피 어댑터와 가짜 발송기(`FakeProvider`)를 구현합니다.
- 가짜 발송기는 접수 즉시 `sent`를 돌려주고, 1\~5초 뒤 성공 90%·실패 10%로 웹훅을 스스로 호출합니다. 체험 계정과 테스트는 항상 가짜 발송기를 씁니다.
- 솔라피를 고른 이유: 개인도 본인 휴대폰 번호로 발신번호 등록 가능, 가입 시 테스트 포인트, REST API와 Node SDK, 발송 결과 웹훅 지원(확인 필요). 대안 NHN Cloud는 기업용 설정이 무겁고, 알리고는 결과를 조회 방식으로 받아 "나중에 온다"는 설계를 보여 주기 약합니다.
- 실제 발송 안전장치: 환경 변수로 허용 수신번호 목록(내 번호)과 하루 상한(10건)을 두고, 어댑터 앞단에서 코드로 막습니다. 체험 계정은 설정과 무관하게 가짜 발송기 고정.

**2. 발송 결과 웹훅**

- 경로 `POST /api/webhooks/sms/[provider]`. 순서: 서명 검증 → 원문을 `webhook_events`에 저장 → 메시지 행 상태 전이(최종 상태면 무시) → 발송 건 집계 갱신 → Supabase Realtime이 화면에 전달.
- 같은 이벤트가 두 번 와도, 순서가 뒤바뀌어도 결과가 같아야 합니다(데이터 모델의 전이 규칙). 서명이 틀리면 401로 거부하고 기록만 남깁니다.
- 로컬 개발은 nanaki 때 쓴 터널로 받습니다. 가짜 발송기는 같은 경로를 호출하므로 터널 없이도 흐름 전체를 돌릴 수 있습니다.

**3. 충전금 결제: 토스페이먼츠 테스트 모드**

- 흐름: 계정 주인(본사 또는 지점)이 금액 선택 → 서버가 `payments`에 `ready` 행과 주문번호 생성 → 결제위젯 호출 → 성공 리다이렉트로 돌아온 `paymentKey·orderId·amount`를 서버가 **DB의 금액과 대조**한 뒤 승인 API 호출 → `done` + `ledger_entries.charge` 기록(같은 트랜잭션).
- 웹훅은 보조 확정 수단입니다. 리다이렉트가 끊겨도 웹훅으로 `done`이 들어오면 같은 처리를 하되, 결제 키 기준 멱등 처리로 두 번 충전되지 않게 합니다.
- 승인은 됐는데 거래 기록 저장이 실패한 경우: 승인 전에 `ready` 행이 있으므로, 조회 API로 상태를 맞추는 복구 작업을 설정 화면에서 수동 실행할 수 있게 합니다(2차: 자동).
- 포트원 대신 토스를 직접 붙이는 이유: 중간 계층 없이 승인·웹훅·멱등을 내가 다뤘다는 이야기가 분명해집니다.

## 발송 큐와 재시도

별도 큐 서버 없이 **DB를 큐로** 씁니다. `messages` 테이블의 `queued` 행이 곧 큐이고, pg\_cron이 주기적으로(예: 10초) Edge Function 워커를 깨워 한 묶음씩 집어 업체에 보냅니다. 규모(1만\~10만 건)에 비해 Redis·전용 큐는 과하고, Vercel 함수는 실행 시간 제한 때문에 긴 작업에 맞지 않습니다.

- **중복 집기 방지**: 워커는 `SELECT … FOR UPDATE SKIP LOCKED LIMIT n`으로 행을 잠그고 가져옵니다. 워커 두 개가 동시에 떠도 같은 행을 두 번 보내지 않습니다.
- **묶음과 전송 제한**: 한 번에 100\~500건을 묶어 보내고, 업체 초당 제한에 맞춰 묶음 사이에 간격을 둡니다. 숫자는 업체 문서 확인 뒤 환경 변수로 뺍니다.
- **실패 분류**: 일시 오류(네트워크, 5xx, 업체 점검)는 `nextAttemptAt`을 1분 → 5분 → 30분으로 늘려 최대 3회 재시도. 영구 오류(잘못된 번호, 수신거부, 잔액 부족)는 즉시 `failed`로 확정하고 재시도하지 않습니다.
- **멱등성**: 메시지마다 우리 쪽 고유 키를 만들어 업체에 함께 보내고, 재시도에도 같은 키를 씁니다. 업체가 지원하면 업체 쪽에서 중복이 막히고, 지원하지 않으면 `providerMessageId`가 이미 있는 행은 다시 보내지 않는 것으로 우리 쪽에서 막습니다.
- **예약 발송**: 같은 큐에 `scheduledAt`만 더합니다. 워커는 `scheduledAt <= now()`인 행만 집습니다.
- **진행률**: 발송 건의 집계(접수·도착·실패 수)는 메시지 행이 바뀔 때 DB 트리거가 갱신하고, 화면은 발송 건 행 하나만 Realtime으로 구독합니다. 10만 행을 모두 구독하지 않습니다.
- **멈춘 발송 감지**: `sent` 상태로 일정 시간(예: 1시간) 이상 결과가 안 오면 업체 조회 API로 상태를 맞추는 보정 작업을 pg\_cron에 둡니다(2차).

| 3 | 1만 건 발송 처리 시간 | 묶음 1건씩 | 묶음 100 / 500건 비교 | 가짜 발송기 기준, 접수부터 전체 완료까지 DB 타임스탬프 차이 |
| 4 | 웹훅 반영 지연 | 폴링 10초 | Realtime | 웹훅 도착 시각 → 화면 갱신 시각 중앙값, 100건 샘플 |
| 5 | Lighthouse (발송 내역, PC) | 첫 배포 시점 | 출시 시점 | 시크릿 창, 3회 중앙값. nanaki에서 배운 것을 처음부터 적용해 90+ 목표 |

여기에 단위 테스트 수와 RLS 통합 테스트 수를 더해 포트폴리오 첫 화면 수치 3개를 고릅니다.

**테스트 범위**

| 종류 | 대상 | 방법 |
| --- | --- | --- |
| 단위 (Vitest) | 바이트 계산·SMS/LMS 전환 경계, 광고 규칙 검증, 전화번호 정규화, 상태 전이 규칙(역행·중복·역순), 금액 선점·환불 계산, 엑셀 행 검증, 재시도 간격 계산 | 경계값 중심. 개수보다 "무엇을 막는지"를 포트폴리오에 적음 |
| 외부 API | 솔라피·토스 HTTP | MSW로 응답 흉내기(성공·5xx·타임아웃·중복 웹훅). 서명 검증은 실제 알고리즘으로 양성·음성 케이스 |
| 통합 | RLS 권한 | 실제 Supabase에 대고 역할 2개로 남의 지점 데이터가 안 보이는지, 지점이 다른 지점 잔액을 못 쓰는지. 잔액 선점 함수를 동시 호출해 음수가 안 나는지 |
| E2E (Playwright) | 한 흐름: 체험 → 엑셀 업로드 → 광고 작성 → 역할 전환 → 승인 → 발송 → 결과 반영 | 크로미움 PC. 승인함만 WebKit 모바일 프리셋 추가 |
| 화면 비교 | 핵심 화면 4개(첫 화면·발송 내역·문자 작성·승인함) × 1280·1440 | Playwright 스크린샷 |

**CI/CD (GitHub Actions)**: PR마다 lint → typecheck → 단위 → build → E2E(가짜 발송기) → 화면 비교. RLS 통합은 main 머지 시. Lighthouse CI는 발송 내역 화면 1개. Vercel이 PR 프리뷰·main 배포. Supabase 마이그레이션은 CLI로 버전 관리하고 main 배포 전에 적용.

## 디자인과 일정

**디자인 (2\~3일, 코드 전)**: nanaki 토큰(`nanaki-tokens.json`)을 가져와 브랜드 색만 바꿉니다. 시안은 핵심 화면 3개만(발송 내역 표, 문자 작성 + 미리보기, 첫 화면). 나머지는 shadcn/ui 기본 모양에 토큰만 입힙니다. 가장 공들이는 화면은 발송 내역 표(포트폴리오 첫 캐처). 관리자 콘솔의 디자인 기준은 "예쁘가"보다 "표가 읽기 쉬운가, 실수를 막는가"입니다. 디자인 캔버스 프롬프트는 nanaki 때처럼 따로 준비합니다.

**step별 계획 (step이 끝날 때마다 배포, 전체 약 5주 목표)**

| step | 목표 | 끝났을 때 보이는 것 |
| --- | --- | --- |
