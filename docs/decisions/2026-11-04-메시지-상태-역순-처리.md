# 메시지 상태의 역순 도착 처리

2026-11-04 · `src/features/campaigns/status.ts`

## 문제

워커가 업체 응답을 받아 `sent`를 저장하기 전에 결과 웹훅이 먼저 도착할 수 있다. 기획서의 "`sent → delivered / failed`만 허용"을 그대로 적용하면 이 웹훅은 버려지고, 업체가 다시 보내지 않으면 메시지가 영영 확정되지 않는다.

## 결정

| 상황 | 처리 |
| --- | --- |
| `queued`에 결과 웹훅 도착 | 바로 최종 상태로 확정한다 |
| 최종 상태에 뒤늦은 접수 기록 도착 | 상태는 유지하고 비어 있는 업체 id와 접수 시각만 채운다 |
| 최종 상태에 다른 결과 웹훅 도착 | 먼저 온 결과를 유지하고 `webhook_events`에만 남긴다 |
| `sent`에 워커의 실패 기록 도착 | 무시한다. 업체가 이미 받았으므로 결과는 웹훅이 정한다 |

## 버린 대안

- **웹훅을 보류했다가 다시 처리**: 재처리 작업과 보류 상태가 더 필요하다. 결과는 이미 사실이므로 기다릴 이유가 없다.
- **웹훅 처리를 실패로 돌려 업체 재전송에 의존**: 업체의 재전송 규칙에 묶인다. 재전송 여부는 아직 공식 문서로 확인하지 않았다.

## 한계

- `delivered`와 `failed`가 같은 메시지에 모두 오면 도착 순서에 따라 결과가 달라진다. 정상 업체라면 생기지 않는 경우로 보고 원문을 `webhook_events`에 남겨 추적한다.
- `status.ts`는 순수 함수다. 동시 요청은 호출하는 쪽이 저장할 때 `where status = 읽은 상태`로 막아야 하며, 이는 워커와 웹훅을 만드는 step4에서 구현하고 테스트한다.
