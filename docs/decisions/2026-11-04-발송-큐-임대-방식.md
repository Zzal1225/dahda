# 발송 큐: 행 잠금 대신 임대, 코드는 src 한 곳에

날짜: 2026-11-04

## 문제 1: 잠금은 업체 호출까지 이어지지 않는다

기획서는 `FOR UPDATE SKIP LOCKED`로 중복 집기를 막는다고 적었다. 그런데 워커는 RPC로 행을 집고, 업체 호출은 그 뒤에 한다. RPC가 끝나면 트랜잭션과 잠금도 끝나므로 다음 워커가 같은 행을 집을 수 있다. 업체 호출 동안 트랜잭션을 열어 두면 연결을 오래 점유하고, 함수가 죽었을 때의 처리도 어렵다.

## 결정

집을 때 `SKIP LOCKED`로 동시 집기를 막고, 같은 문장에서 `next_attempt_at`을 5분 뒤로 밀어 임대한다.

- 정상이면 결과 저장이 상태나 다음 시도 시각을 정한다.
- 워커가 저장 전에 죽으면 임대가 끝난 뒤 다시 집힌다. 영영 멈추는 행이 없다.
- 이때 이미 접수된 건이 다시 나갈 수 있으므로 같은 멱등 키로 보내 업체 쪽에서 막는다.
- 임대만 반복되면 횟수 초과로 실패 확정해 무한 반복을 막는다.

버린 대안: `sending` 상태 추가. 메시지 상태를 기획서 4개 밖으로 늘리고, 멈춘 행을 되돌리는 별도 작업이 필요하다.

## 문제 2: Next.js와 Deno가 코드를 함께 쓴다

상태 전이는 `status.ts` 하나로만 바꾼다는 규칙 때문에 워커가 같은 파일을 써야 한다. 코드를 `supabase/functions/_shared`로 복사하면 두 벌이 어긋난다.

## 결정

`src/`의 파일을 Edge Function이 상대 경로로 직접 불러온다. 대신 그 파일들은 다음을 지킨다.

- import에 `@/` 별칭 없이 확장자까지 적는다. 타입 전용 import도 Deno가 경로를 확인한다(실제 부팅 실패로 확인).
- `npm` 패키지는 `supabase/functions/send-worker/deno.json`의 import map으로 잇는다.

단위 테스트는 이 문제를 잡지 못한다. 로컬 Edge Function을 실제로 띄워야 드러난다.

## 야간 광고

접수 때 낮이어도 재시도(최대 30분 뒤)나 긴 발송이 21시를 넘길 수 있다. 워커가 보내기 직전에 다시 확인해 다음 8시로 미루고, 시도 횟수는 돌려준다. 규칙의 출처는 [광고 문자 규칙 기록](2026-11-04-광고-문자-규칙과-바이트-기준.md)이다.

## 운영 적용 시 주의

cron은 Vault의 `send_worker_url`, `send_worker_secret`이 없으면 아무것도 하지 않는다. 마이그레이션을 적용해도 설정 전에는 발송이 시작되지 않는다.

## 운영 적용 순서

Vault를 마지막에 넣는다. Vault가 들어가는 순간 cron이 워커를 깨우기 시작하므로, 그 전에 받을 곳이 모두 준비돼 있어야 한다.

1. 마이그레이션 적용: `npx supabase db push --remote`
2. 임의의 값 2개를 만든다(워커 비밀값, 웹훅 서명 키).
3. Edge Function 환경 변수: `npx supabase secrets set WORKER_SECRET=... FAKE_WEBHOOK_SECRET=... APP_URL=https://dahda-xi.vercel.app`
4. Edge Function 배포: `npx supabase functions deploy send-worker`
5. Vercel Production 환경 변수에 같은 `FAKE_WEBHOOK_SECRET`을 넣고 다시 배포한다.
6. SQL Editor에서 Vault 등록: `select vault.create_secret('https://<프로젝트 ref>.supabase.co/functions/v1/send-worker', 'send_worker_url'), vault.create_secret('<워커 비밀값>', 'send_worker_secret');`

## 확인하지 못한 것

Edge Function의 `SUPABASE_SERVICE_ROLE_KEY` 기본 환경 변수는 로컬에서만 확인했다. 운영 프로젝트는 새 API 키 체계를 쓰므로 배포 후 실제로 동작하는지 확인해야 한다.
