직접 잰 숫자만 적는다. 측정 조건이 다르면 비교하지 않는다.

## 측정 1: 10만 행 발송 내역 표

**스크립트**: `scripts/measure-table.mjs`

**조건**

| 항목 | 값 |
| --- | --- |
| 기기 | AMD Ryzen 5 5600X, RAM 16GB, Windows 10 |
| 브라우저 | Playwright Chromium Headless Shell, 1280×800 |
| 서버 | 같은 PC의 `next start`(프로덕션 빌드)와 로컬 Supabase |
| 데이터 | `npm run db:seed:large`의 메시지 100,000행 |
| 횟수 | 3회 실행의 중앙값 |
| 스크롤 | 5초 동안 맨 위에서 맨 아래까지 일정 속도 |

헤드리스 환경이고 서버와 브라우저가 같은 PC라 실제 사용자 수치가 아니다. 같은 조건의 전후 비교에만 쓴다.

**결과**

변경 전: 모든 행을 받아 모두 렌더. 변경 후: 보이는 페이지만 서버에서 받고 보이는 행만 렌더(TanStack Virtual, 행 36px, 페이지 100건).

| 지표 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 접속부터 표시까지 | 12,391ms | 679ms |
| 데이터 수신 | 3,160ms (1,000행씩 100회) | 80ms (첫 페이지 100행) |
| 데이터 수신 후 표시까지 | 8,705ms | 6ms |
| 표 행 DOM | 100,000개 | 24개 |
| DOM 노드 전체 | 800,086개 | 580개 |
| 메모리(JS 힙) | 179MB | 15MB |
| 스크롤 프레임 | 6fps | 60fps |
| 스크롤 중 가장 긴 프레임 | 233ms | 17ms |
| 50ms 넘는 프레임 | 27개 | 0개 |
| 스크롤을 멈춘 뒤 행이 보일 때까지 | 측정 안 함(이미 그려져 있음) | 215ms |

3회 범위: 변경 전 표시까지 8,423~9,182ms, 변경 후 접속부터 표시까지 670~799ms, 멈춘 뒤 표시까지 215~232ms.

**변경 후의 비용**: 공짜가 아니다. 5초 안에 10만 행을 지나는 빠른 스크롤에서는 실제 행 대신 자리 표시가 보이고, 멈춘 뒤 약 0.2초(요청 지연 120ms 포함) 뒤에 행이 나타난다. 60fps는 이 조건에서 잰 값이다. 변경 전은 모든 행이 이미 있어 이 대기가 없다.

**재현**: 변경 전 코드는 커밋 `92af7b3`(측정 지점을 고친 뒤)의 `src/features/messages/plain-recipient-table.tsx`다. 스크립트의 "멈춘 뒤" 지표는 변경 후에 추가했다.

**해석하지 않는 값**: 변경 전 Long Task는 렌더에 약 9초가 걸렸는데도 약 800ms짜리 1건만 잡혔다. React가 렌더를 작게 나눠 실행했기 때문으로 추정하지만 확인하지 못해 표에서 뺐다.

## 측정 2: 엑셀 업로드 중 화면 반응

**스크립트**: `scripts/measure-upload.mjs [횟수] [행 수] [CPU 저하 배수]`

**조건**: 측정 1과 같은 PC와 브라우저, 프로덕션 빌드, 3회 중앙값. 전화번호·이름·메모 3열 xlsx. 파싱 구간에 50ms 간격으로 화면을 눌러 입력 지연을 잰다. CPU 저하는 Chrome의 `Emulation.setCPUThrottlingRate`로 흉내 낸 근사값이다.

**입력이 막힌 최대 시간**

| 조건 | 메인 스레드 | Web Worker |
| --- | --- | --- |
| 1만 행, 저하 없음 | 58ms | 0.3ms |
| 1만 행, CPU 6배 저하 | 818ms | 62ms |
| 2만 행, 저하 없음 | 142ms | 0.3ms |
| 2만 행, CPU 6배 저하 | 1,528ms | 109ms |

**가장 긴 작업(Long Task)**

| 조건 | 메인 스레드 | Web Worker |
| --- | --- | --- |
| 1만 행, 저하 없음 | 100ms | 없음 |
| 1만 행, CPU 6배 저하 | 839ms | 83ms |
| 2만 행, 저하 없음 | 183ms | 없음 |
| 2만 행, CPU 6배 저하 | 1,571ms | 154ms |

**파싱 시간 (저하 없음)**: 1만 행 100ms → 156ms, 2만 행 180ms → 251ms. **Worker가 오히려 느리다.** Worker를 띄우고 라이브러리를 받고 결과를 복사하는 비용 때문이다.

**읽는 법**

- 개발 PC에서는 1만 행도 100ms라 메인 스레드로도 크게 불편하지 않다. 기획서의 "화면이 멈춘다"는 가정은 이 PC에서는 성립하지 않았고, 느린 PC를 흉내 낸 조건에서만 체감할 수준(0.8~1.5초)이 된다.
- Worker의 이득은 파싱 속도가 아니라 **파싱 중에도 입력이 막히지 않는 것**이다. 또 파싱 중 취소가 가능해지고, SheetJS(379KB)가 업로드 화면 밖의 번들에 들어가지 않는다.
- CPU 저하 조건의 Worker 파싱 시간(270ms, 399ms)은 표에 넣지 않았다. 저하가 Worker 스레드에 적용되지 않는 것으로 보이며, 실제 느린 PC에서는 더 오래 걸린다. 입력 지연은 메인 스레드를 재는 값이라 비교할 수 있다.
- Worker에 남은 지연은 결과를 메인 스레드로 복사하고 화면을 그리는 구간으로 추정한다. 확인하지는 않았다.

**재현**: 변경 전 코드는 커밋 `d492f1f`의 `read-upload.ts`다.

## 측정 3: 1만 건 발송 처리 시간과 묶음 크기

**스크립트**: `scripts/measure-send.mts [묶음 크기] [건수] [웹훅 동시 수]`

**조건**: 측정 1과 같은 PC, `next start`와 로컬 Supabase. 가짜 발송기, 건당 1~5초의 결과 대기는 뺐다. 웹훅은 실제 앱 경로로 동시 20개. 워커를 쉬지 않고 돌려 처리 능력을 쟀다. 시간은 DB의 접수 시각, 마지막 `sent_at`, 완료 시각의 차이다. 3회 중앙값.

| 묶음 크기 | 건수 | 접수까지 | 초당 접수 | 전체 완료 |
| --- | --- | --- | --- | --- |
| 1 | 1,000 | 14.1초 | 71건 | 14.1초 |
| 100 | 10,000 | 14.4초 | 696건 | 37.3초 |
| 500 | 10,000 | 4.1초 | 2,455건 | 37.2초 |

**해석**

- 묶음 1은 1만 건을 끝까지 돌리지 못했다. 도중에 `fetch failed`로 멈췄고, 이때 PC의 TIME_WAIT 소켓이 1만 2천 개를 넘었다. Windows의 임시 포트 고갈로 보이며 앱의 한계로 단정하지 않는다. 그래서 1,000건으로 쟀고, 규모가 달라 전체 완료 시간은 다른 행과 비교할 수 없다.
- 묶음을 키우면 접수는 빨라지지만(묶음 1 대비 약 10배, 35배) 전체 완료는 같다. 1만 건에서 37초의 대부분이 건별 웹훅 처리이고, 동시 20개 기준 초당 약 270건이다.
- 가짜 발송기는 네트워크 비용이 없다. 실제 업체를 붙이면 접수 수치는 달라진다.

### 재측정: 수신자 기록을 남긴 뒤 (2026-11-06)

수신자 기록(`message_events`)을 더하면서 워커 묶음마다 1번, 웹훅 요청마다 1번 DB 호출이 늘었다. 처리량이 떨어졌는지 같은 날, 같은 PC에서 전후를 함께 쟀다.

**조건**: 위와 같다. 묶음 500, 1만 건, 웹훅 동시 20, 3회 중앙값. 전은 기록이 들어가기 직전 커밋 `dfc2ac1`, 후는 그 기록이 들어간 main. 후 측정에서 발송 건마다 기록 20,000줄(접수 1만 + 결과 1만)이 남은 것을 DB에서 확인했다.

| | 접수까지 | 전체 완료 | 3회 전체 완료 |
| --- | --- | --- | --- |
| 전 (`dfc2ac1`) | 4.3초 | 35.2초 | 35.2 / 35.3 / 35.1초 |
| 후 (기록 추가) | 4.1초 | 35.7초 | 36.5 / 35.6 / 35.7초 |

**해석**

- 전체 완료가 약 0.5초(1.4%) 늘었다. 1만 건을 전체 완료 시간으로 나누면 초당 약 284건에서 약 280건이다.
- 접수까지는 실행마다 3.3~7.4초로 흔들려 전후 차이를 말할 수 없다.
- 위 표의 37.2초와는 날짜와 PC 상태가 달라 직접 비교하지 않는다.

**알아낸 제약**: 실제 운영은 cron이 10초마다 한 묶음만 처리한다. 계산하면 1만 건에 묶음 100은 1,000초, 묶음 500은 200초다. 위 처리 능력보다 cron 주기가 먼저 한계가 된다(이 두 값은 계산값이다). 묶음 크기는 솔라피 초당 제한을 확인하는 4-4에서 정한다.

## 측정 4: 웹훅 반영 지연

**스크립트**: `scripts/measure-webhook-latency.mts [표본 수]`

**조건**: 측정 1과 같은 PC와 브라우저, 프로덕션 빌드. 100개 표본. 서명한 웹훅을 보내기 직전부터 선택한 행의 진행률 숫자가 바뀐 프레임까지 잰다. 표본 사이는 0~10초에서 임의로 쉰다. 서버와 브라우저가 같은 PC라 배포 환경의 네트워크 지연은 들어 있지 않다.

| 방식 | 중앙값 | 90% | 최소 | 최대 |
| --- | --- | --- | --- | --- |
| 폴링 10초 | 5,164ms | 8,671ms | 221ms | 9,092ms |
| Realtime | 274ms | 537ms | 49ms | 762ms |

중앙값 기준 약 19배 빨라졌다. 처음에는 폴링을 중앙값 8,453ms로 쟀는데, 표본 사이를 0~3초만 쉬어 웹훅이 항상 주기 앞쪽에 몰린 탓이었다. 최솟값이 7초인 것을 보고 찾아 다시 쟀고, 이 값은 쓰지 않는다.

변경 전후 모두 웹훅이 몰리는 상황은 재지 않았다. 몰리면 화면 갱신을 1초에 한 번으로 묶으므로 지연이 최대 약 1초 늘어난다.

## 추가 측정: 함수 리전과 화면 응답 시간

**스크립트**: `scripts/measure-page-speed.mjs [기준 주소] [반복 횟수]`

**조건**: 운영 사이트(`dahda-xi.vercel.app`), 측정 1과 같은 PC에서 headless Chromium, 1440×900, 체험 계정 1개. 화면 4개를 6회 재고 첫 회차는 콜드 스타트가 섞일 수 있어 뺀 5회의 중앙값이다. 새로고침은 문서 요청 시작부터 응답 스트림 끝까지, 메뉴 클릭은 클릭부터 그 화면의 RSC 요청 끝까지다. 브라우저가 그리는 시간은 들어 있지 않다.

**원인**: 응답 헤더 `x-vercel-id`가 `icn1::iad1`이었다. 서울로 들어온 요청을 미국 동부 함수가 처리하고, 함수는 서울의 Supabase를 부른다. 쿼리는 호출이 많은 것도 평균 0.3~5.3ms로 빨랐으므로 DB 호출마다 생기는 왕복을 의심했다.

**변경 전** (`iad1`, 2026-11-05 측정):

| 화면 | 새로고침 | 메뉴 클릭 |
| --- | --- | --- |
| 홈 | 1,593ms | 1,418ms |
| 주소록 | 1,787ms | 1,753ms |
| 문자 작성 | 1,672ms | 1,683ms |
| 발송 내역 | 2,075ms | 1,813ms |

처음 잰 TTFB는 13ms였지만 쓰지 않는다. Cache Components의 정적 껍데기가 CDN에서 먼저 나가기 때문이고, 그때 화면에는 데이터가 없다. 메뉴 클릭도 처음에는 50ms, 136ms로 나왔는데 각각 networkidle이 바로 끝난 것과 스크립트가 요청을 놓친 것이어서 버렸다.

**변경 후** (`icn1`, 같은 날 측정):

| 화면 | 새로고침 전 → 후 | 메뉴 클릭 전 → 후 |
| --- | --- | --- |
| 홈 | 1,593 → 391ms | 1,418 → 344ms |
| 주소록 | 1,787 → 457ms | 1,753 → 452ms |
| 문자 작성 | 1,672 → 453ms | 1,683 → 406ms |
| 발송 내역 | 2,075 → 420ms | 1,813 → 398ms |

새로고침은 73~80% 줄었다. 체험 계정의 샘플 데이터 기준이고 로그인 사용자의 실제 계정은 재지 않았다.

**메뉴 클릭 비교의 한계**: 변경 후에는 라우터가 응답을 받은 뒤 요청을 취소(`ERR_ABORTED`)해 `finished()`가 끝나지 않았다. 그래서 변경 후 값은 완료와 취소 중 먼저 온 시각까지다. 변경 전에는 완료까지만 쟀으므로 끝 지점이 완전히 같지는 않다. 취소가 변경 후에 나타난 이유는 확인하지 못했다. 사용자 영향은 없었다. 본문은 클릭 후 약 0.1초에 바뀌고 응답은 0.3초 안에 왔다.
